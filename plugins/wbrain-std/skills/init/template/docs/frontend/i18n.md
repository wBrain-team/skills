# Internacionalização (i18n) — `react-i18next`

[← Frontend](frontend.md)

O i18n é habilitado **desde o início** com `react-i18next` + `i18next`, mesmo que só
exista `pt-BR` hoje — assim nenhuma string nasce hardcoded e adicionar um idioma é só
incluir um arquivo de tradução.

## Setup

```ts
// lib/i18n.ts
import i18n from "i18next"
import { initReactI18next } from "react-i18next"
import ptBR from "../locales/pt-BR"

i18n.use(initReactI18next).init({
  resources: { "pt-BR": { translation: ptBR } },  // namespace único
  lng: localStorage.getItem("lang") ?? "pt-BR",
  fallbackLng: "pt-BR",
  interpolation: { escapeValue: false }, // React já escapa
})

export default i18n
```

Importe `lib/i18n` uma vez no entrypoint do app (antes de renderizar). As traduções
ficam num **namespace único**, divididas em um arquivo por domínio; o `index.ts` de cada
idioma junta os arquivos sob a chave do domínio:

```
locales/
└── pt-BR/
    ├── index.ts        # export default { common, auth, errors, roles, users, audit }
    ├── common.json     # botões e rótulos genéricos  → t("common.save")
    ├── auth.json       # login, logout, sessão       → t("auth.fields.email")
    ├── errors.json     # por code do contrato de erro → t("errors.NOT_FOUND")
    ├── roles.json      # valores de enum             → t("roles.admin")
    └── users.json      # telas de usuários            → t("users.fields.name")
```

Chaves seguem `<domínio>.<grupo>.<chave>`, em inglês e snake_case (ex.:
`users.errors.load`), exceto em `errors`, que usa o `code` da API como está.

## Uso

```tsx
import { useTranslation } from "react-i18next"

function SaveButton() {
  const { t } = useTranslation()
  return <Button>{t("common.save")}</Button>          // nunca "Salvar" hardcoded
}

// interpolação e plural
t("users.count", { count })   // "1 usuário" / "3 usuários"
```

**Regras:**
- **Nunca** hardcode string visível ao usuário num componente — sempre via `t()`.
- Troca de idioma: `i18n.changeLanguage("en")` e persiste a escolha em `localStorage`.
- **Erros da API**: o backend mantém o `code` estável (ver [Contrato da API](../backend/api-contract.md)); o frontend
  traduz por `t('errors.<code>')` no `getApiErrorMessage` (`lib/errors.ts`), com fallback para a `message`.
  Os textos do backend permanecem em PT-BR.
- **Rótulos de valores de domínio** (papéis, operações de auditoria) são chaves de
  tradução desde o início — ``t(`roles.${role}`)`` —, nunca mapas de texto fixo (ver
  [Rótulos de domínio](shared-utilities.md#rótulos-de-domínio--i18n--liblabelsts)).
- **Mensagens de validação** (Zod) também vêm do `t` (ver [Formulários](forms.md)).
